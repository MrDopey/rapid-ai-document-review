# Phase 0 Research: Linear Thread Mode

## R1: One shared Pi session per threaded-conversation document, not one session file per thread

**Decision**: A threaded-conversation document gets exactly one Pi session file for its entire lifetime (`<piSessionDir>/thread-tree.jsonl`), created when the document (and its root thread) is created. Every `Thread` (the root and every branch) is a row in the existing `conversation` table pointing at that **same** `piSessionPath`, plus a new column, `piLeafEntryId: string | null`, recording which entry in that shared session tree is that thread's own current tip. Sending a message on a given thread now means: `SessionManager.open(thread.piSessionPath)` → `sessionManager.branch(thread.piLeafEntryId)` (repositions the shared session's leaf pointer to this thread's own tip) → append the message → update `thread.piLeafEntryId` to the newly appended entry's id. Creating a branch means picking the anchor entry id (resolved from the highlighted message, R2) and creating a new `conversation` row with `piSessionPath` equal to the source thread's `piSessionPath` and `piLeafEntryId` equal to that anchor entry id (no new message appended yet — same "seed but don't append a real turn" shape `sendBranchSeedMessage` already uses for canvas branches).

**Rationale**: This is the only way to satisfy FR-006 (a branch MUST be a genuine branch of the *same underlying Pi session* — i.e. `SessionManager.branch()`'s leaf-repositioning within one file) rather than an independently forked session file. `SessionManager.branch(branchFromId)`'s own doc comment is explicit: "Moves the leaf pointer to the specified entry. The next appendXXX() call will create a child of that entry" — this is a single mutable pointer *per session file*, so genuinely sharing Pi-level branch ancestry across N threads requires those N threads to be N leaf positions within one file, not N separate files with a copied prefix.

**Alternatives considered**:
- Reuse the canvas-mode `SessionManager.forkFrom()` pattern (one file per conversation row, branch = copy history into a new file). Rejected: this is explicitly what FR-006/Clarifications rule out — `forkFrom` produces an independent session, not a real shared-tree branch, and the constitution (Principle II) plus this feature's own Clarifications treat that distinction as load-bearing, not cosmetic.
- Model each Thread as its own `SessionManager` instance opened against the shared file, calling `branch()` on every read too. Rejected: `branch()` mutates the file's leaf pointer as a side effect, so any read-only concurrent access (e.g. rendering a non-tip segment, User Story 2 scenario 8) must never call it — only the actual "send a message on the tip" path may reposition the leaf. Read paths (`getTree()`, `getBranch(fromId)`, `getEntries()`) never move the leaf and are always safe to call from any thread's context.

## R2: Highlighted-passage anchor resolves to a Pi entry id, not a document character offset

**Decision**: Unlike canvas mode's `seedSelection` (a document-content character range, `{from, to, text}`), a thread branch's anchor is a **message-and-passage** pair: `{ anchorMessageId: string, highlightedText: string }`, where `anchorMessageId` is an application `MessageDto.id` (from `ConversationService.buildMessages`) belonging to the source thread, resolved server-side to the underlying Pi session entry id it corresponds to (message ids and Pi entry ids are already correlated 1:1 via the existing event log — `message_completed` events already carry the same id Pi assigns via `appendMessage`/`appendCustomMessageEntry`... concretely, the branch endpoint looks up the source thread's own `SessionManager`, finds the entry whose rendered text contains `highlightedText` at or after `anchorMessageId`'s position, and uses that entry's id as the new thread's `piLeafEntryId`). `highlightedText` is validated server-side to actually be a substring of that message's rendered text (reject otherwise) before being used as the FR-005a seed excerpt.

**Rationale**: The thing being highlighted is prior *conversation* text (an agent or user message), not the *document* — there is no document revision/offset concept to reuse here, so this feature's "seed selection" is a different shape from spec 005's, despite the superficial similarity ("a highlighted passage").

**Alternatives considered**: Reusing `SeedSelection {from, to, text}` verbatim against message text (message-local offsets). Rejected as unnecessary precision: FR-005a only needs the exact highlighted substring for the blockquote-style XML seed, not a live-revalidated offset range (messages, unlike document content, are never edited in place after being sent, so there is no "orphaned anchor" concept — spec 005's `anchorOrphaned` field has no analogue here and is explicitly out of scope, Assumptions).

## R3: "Done" is a new, orthogonal field — not a repurposed `status: 'closed'`

**Decision**: Add `doneAt: string | null` to the `conversation` table (used only by `kind: 'thread-root'`/`'thread-branch'` rows). A thread is "done" iff `doneAt !== null`; this is independent of `status` (`idle`/`working`/`errored`), which continues to describe turn-execution state exactly as today. Marking done sets `doneAt`; there is a symmetric "reopen" action that clears it back to `null`. The existing pending-staged-edits guard that blocks `close()` (`ConversationService.close`'s `PendingEditsBlockCloseError`) is extracted into a small shared check reused by both `close()` and the new `markDone()`, so FR-010 is enforced with the same rule, not a re-derivation of it.

**Rationale**: The spec's own Edge Cases require branching from a done thread to succeed (`branch()`'s existing `if (parent.status === 'closed') throw ConversationClosedError` would incorrectly forbid this if "done" reused `status: 'closed'` verbatim) and require a done thread to remain otherwise fully functional (still branchable, still readable) — "done" is a pure visibility/declutter flag, not a lifecycle terminal state the way `closed` is for canvas mode (which also stops it from ever being sent to again, and enables fold-summary/review flows that have no analogue in this feature). Reusing `status: 'closed'` would inherit all of that unwanted canvas-specific behavior.

**Alternatives considered**: A new `ConversationStatus` value `'done'` alongside `idle`/`working`/`errored`/`closed`. Rejected: `status` already encodes "is a turn currently in flight / did the last turn fail," which is orthogonal to "should this be decluttered from the default view" — a `working` thread could plausibly still be marked done as its very last message resolves; conflating the two axes into one enum would make that combination unrepresentable.

## R4: Seed excerpt uses the constitution's existing XML-tag convention, not a new Markdown-blockquote format

**Decision**: A branch's seeded first message is `<branch-seed-excerpt>${highlightedText}</branch-seed-excerpt>` followed by a newline, ahead of whatever the reviewer types next in that same compose action — reusing `buildBranchSeedMessage`/`buildSelectionOnlySeedMessage`'s existing pattern in `seed-excerpt.ts` (which already wraps document content in matching XML tags for canvas-mode seeds) rather than introducing a second seed-formatting convention.

**Rationale**: Constitution, Quality & Review Gates: "Document content embedded in any seed/context message sent to the LLM (e.g. a Main conversation's seed message, a branch's seed excerpt) MUST be wrapped in a matching pair of XML-style tags." This already covers thread branches by name ("a branch's seed excerpt") — no new rule or amendment is needed, only a new tag name (`branch-seed-excerpt`) added alongside the existing `document-revision-N` convention in `seed-excerpt.ts`.

## R5: Rendering split into segments is 100% frontend-derived; no new schema for it

**Decision**: A thread's "segments" (User Story 2 scenarios 6-9, FR-005b) are computed purely in the frontend from data that already exists: for a given Thread, walk its own message list; every message that is some *other* thread's `forkedFromMessageId`-equivalent anchor point (the resolved `anchorMessageId` from R2) becomes a segment boundary. No `ThreadSegment` table or API field is introduced — the backend keeps returning one flat message list per thread (`GetConversationResponse`, unchanged shape) plus the existing `parentId`/branch-anchor metadata on every thread in the document; the frontend groups a thread's own messages into segments and renders sibling branches at each boundary (left-aligned continuation, indented forks, FR-005b).

**Rationale**: Keeps the backend data model exactly what FR-015 asks for (reuse existing conversation/message machinery unchanged) and matches spec 005's own precedent (`ConversationLayout` in specs/005/data-model.md is entirely frontend-derived, never persisted or sent over the wire).

**Alternatives considered**: Backend-computed `segments: ThreadSegment[]` field on `ConversationDto`. Rejected: every input needed (the thread's own messages, plus every other thread's anchor message id) is already present in the existing "list all threads for a document" response; duplicating that computation server-side would be a second source of truth for a purely presentational grouping, with no functional need driving it.

## R6: No Primary / auto-apply concept in threaded-conversation documents

**Decision**: `Thread` rows are never eligible for `isPrimary`; no "Make Primary" action is offered in threaded-conversation mode's UI, and `PrimaryService.designate()` is never called for a `kind: 'thread-root'`/`'thread-branch'` conversation. Every staged edit proposed in any thread goes through ordinary manual review (`autoApplied: conversation.isPrimary && ...` in `edit-service.ts` naturally evaluates to `false` for every thread, since `isPrimary` stays `false` unconditionally — no code branch needs to change).

**Rationale**: Constitution Principle III's auto-apply carve-out is scoped to "the Primary conversation," a canvas-mode concept the spec never mentions extending to this feature; User Story 1's "no privileged thread" framing (every top-level... now single-root... thread has equal standing) is consistent with *no* thread getting the elevated auto-apply privilege either. This requires no code change beyond never wiring the "Make Primary" UI affordance into the threaded-conversation view.

## R7: Document type is a new, creation-time-fixed column

**Decision**: Add `documentType: 'canvas' | 'thread'` to the `document` table, `NOT NULL DEFAULT 'canvas'` (so every pre-existing document from specs 001/005/010 is unambiguously `'canvas'` after migration). `DocumentService.create()` gains a `documentType` parameter (spec 010's `POST /api/documents` request body gains an optional `documentType` field, defaulting to `'canvas'`); when `'thread'`, `create()` calls a new `ThreadService.createRoot(documentId)` instead of `ConversationService.ensureMain(documentId)`. There is no route or method to change `documentType` after creation (FR-014).

**Rationale**: Directly implements the 2026-09-20 Clarification. Reusing spec 010's existing document-creation request/response shapes (rather than a parallel "create a threaded document" endpoint) keeps one document-creation code path with a type switch, matching FR-015's reuse mandate.

## R8: Export/render (User Story 4, FR-013) is out of scope for this plan

**Decision**: This plan covers User Stories 1-3 (FR-001 through FR-012, FR-014, FR-015) only. User Story 4 / FR-013 remained blocked on the constitution amendment removing the "Pi export viewing" non-goal (spec Assumptions, "Blocking prerequisite"); no research, data model, contract, or task is produced for it here. A follow-up `/speckit-plan` run extends this plan once that amendment lands.

**Rationale**: Per Key rules ("ERROR on gate failures or unresolved clarifications"), a genuine, undischargeable constitution conflict for one user story should not block planning the stories that don't depend on it — the spec itself already documents this split as intentional, not an oversight.

**Follow-up (2026-09-20)**: The blocking constitution amendment has landed (constitution v2.4.0): "Pi export viewing" is no longer a non-goal, narrowly carved out to permit read-only rendering of a thread's genuine, native Pi session export obtained via the Pi SDK (Principle II unaffected — no direct reading/writing of Pi's underlying session storage format, and no fabricated/reformatted substitute for Pi's own export). User Story 4 / FR-013 is therefore unblocked for planning; this R8 entry and its "out of scope" decision above describe this plan's original scope and remain historically accurate. See R9 below for the actual design, produced in this follow-up planning pass.

## R9: Export uses `SessionManager.createBranchedSession()` on a throwaway instance, not `AgentSession.exportToJsonl()`/`exportToHtml()`

**Decision**: `PiService.exportThreadSession(thread)` opens a **fresh, throwaway** `SessionManager.open(thread.piSessionPath)` (never the cached, shared instance in `threadSessionManagers` — see the gotcha below), then calls `sessionManager.createBranchedSession(thread.piLeafEntryId)`. This is a genuine, public `SessionManager` method (`@earendil-works/pi-coding-agent`'s own doc comment: "Create a new session file containing only the path from root to the specified leaf. Useful for extracting a single conversation path from a branched session.") — it writes a real, standalone Pi session `.jsonl` file to disk containing exactly this Thread's own root-to-leaf history, with its own genuine session header (`parentSession` pointing back at the shared file). The new file is then reopened read-only (`SessionManager.open(newPath)`), its raw bytes are read via `fs.readFileSync` for the literal export artifact, and its entries are walked with the same `extractPlainMessageText` helper `readClosedTranscript` already uses to build a friendly `{ role, text }` list for rendering. The temporary export file is deleted (`fs.unlinkSync`) immediately after being read — nothing is persisted (Key Entities: "Exported session ... produced on demand"), so this remains ephemeral, on-demand output, not a new stored artifact.

**Rationale**:
- `AgentSession.exportToJsonl()`/`.exportToHtml()` (the SDK's own higher-level export methods) are the more obvious-looking candidates, but both require a **live** `AgentSession` instance (`this.state`, tool renderer, model), which `FakeAgentSession` (`RADR_BE_PI_FAKE_SESSIONS=1`, the mode this codebase's entire integration/contract test suite runs under) does not provide and has no reason to fake — precedent already exists for read-only Pi-history operations degrading gracefully under fake sessions (`readClosedTranscript` returns `null` there). Building export on top of `AgentSessionLike`/`FakeAgentSession` would mean either faking a whole HTML/JSONL exporter for tests (a second, parallel implementation of "genuine Pi export" that isn't genuine at all) or leaving the feature untestable under this repo's standard test mode.
- By contrast, every Thread already has a **real, always-instantiated** `SessionManager` backing its shared session file regardless of `RADR_BE_PI_FAKE_SESSIONS` (`PiService.threadSessionManagers`/`prepareThreadSession` — `sendOnThread`'s fake-session branch explicitly appends both the user's and the fake assistant's text to this same real `SessionManager` precisely so the shared-tree bookkeeping stays genuine even with no live model in the loop). `createBranchedSession()` operates purely on this always-real `SessionManager`, so the export feature is exercised identically, and just as genuinely, under both fake and real sessions — no test-only stand-in is needed.
- The package's `exports` map (`package.json`) only allows importing from `.`, `./rpc-entry`, `./client` — the free function `exportSessionToJsonl`/`exportSessionToHtml` (`core/session-export.ts`, `core/export-html/`) are not part of that surface, so calling them directly (bypassing `AgentSession`) is not an option; `SessionManager.createBranchedSession()` is a fully public method on the one exported class this module already imports, so it introduces no new SDK surface beyond what `PiService` already touches.
- **Critical gotcha, why a *throwaway* instance**: `createBranchedSession(leafId)` does not just write a new file — it **mutates the calling `SessionManager` instance in place**, repointing its own `sessionFile`/`sessionId`/`fileEntries` at the newly created branched session (the SDK's own fork/clone primitive is built to *become* the new session, not to leave the original untouched). Calling it on the cached, shared `threadSessionManagers.get(thread.id)` instance would silently corrupt every other Thread's shared-tree bookkeeping for that document from that point on (`sendOnThread`/`resolveThreadAnchorEntryId` would keep reading from the wrong file/entry-id space). `exportThreadSession` therefore always opens its own fresh `SessionManager.open(thread.piSessionPath)` for this one operation and never touches `threadSessionManagers`.
- A thread with no messages yet (`piLeafEntryId === null`) has no history to export — `createBranchedSession` itself throws ("Entry ... not found") on an empty path. `ThreadService.exportSession` checks `buildConversationMessages(...).length === 0` first and throws a dedicated `EmptyThreadExportError` (→ `409`/`EMPTY_THREAD_EXPORT`) rather than surfacing the SDK's own generic error text.

**Alternatives considered**:
- `AgentSession.exportToHtml()`/`.exportToJsonl()` on a live session. Rejected per the fake-session testability problem above, and because it would require standing up a full live session (model resolution, tool wiring) just to serve a read-only export, when nothing about producing the export needs a model or tools at all.
- Re-deriving the thread's history purely from the application's own event log (`buildConversationMessages`), formatted to look like a Pi session file. Rejected outright: this would be exactly the "fabricated/reformatted substitute for Pi's own export" the constitution amendment explicitly excludes — the whole point of FR-013 is that the rendered content is Pi's own genuine export, not the application's transcript reformatted to resemble one.
- Persisting the exported file permanently (e.g. under the document's session directory) for later re-download. Rejected: the spec's Key Entities describe the export as "produced on demand," with no requirement to store or re-serve a previous export; generating fresh (matching "the thread's actual message history at export time" precisely, acceptance scenario 2) and discarding avoids unbounded disk growth from repeated exports.

**Rendering**: The frontend renders the parsed `{ role, text }` list through the exact same `MessageBubble.vue` component (and its existing sanitized Markdown pipeline, Principle VI) already used for a Thread's live transcript — reused, not reimplemented, per FR-015's spirit. The literal raw JSONL bytes are shown alongside, in a collapsible `<pre>` block using plain text interpolation (never `v-html`), which is what makes the view demonstrably "the underlying Pi session export itself" (spec's "Why this priority") rather than only the application's own transcript view: the raw panel is byte-identical to what `SessionManager.createBranchedSession` actually wrote to disk, not a re-derived approximation.

## R10: Document-wide export uses `AgentSession.exportToHtml()` on a brand-new, uncached session, never a session already cached for turn execution

**Decision**: `PiService.exportDocumentSession(threads: ConversationRow[])` produces a document-wide export (FR-013b) covering the ENTIRE shared per-document Pi session file — every Thread's own branch together — as a single self-contained HTML artifact, via the Pi SDK's own `AgentSession.exportToHtml(outputPath?)`. Unlike `exportThreadSession`'s `SessionManager.createBranchedSession()` (R9, which extracts one Thread's own root-to-leaf path into a NEW standalone file), `exportToHtml()` renders `SessionManager.getEntries()` — the whole file, every Thread's branch at once, with client-side JS to navigate between them — which is the SDK's only whole-tree-in-one-artifact primitive and therefore the only way to satisfy FR-013b without the application fabricating its own multi-branch renderer (constitution v2.5.0's express boundary).

`exportToHtml()` is a method on the real `AgentSession` (unlike `SessionManager`, which every Thread already has instantiated regardless of fake/real sessions — R9's own gotcha), so producing this export needs a live, fully-wired `AgentSession`. This method always builds a BRAND-NEW one for the document's `thread-root`, via `getOrCreateSession(root, undefined, { skipCache: true })` — a new option added to `getOrCreateSession` that skips both reading AND writing `PiService.sessions`, the per-conversation turn-execution cache every ordinary send reuses — then disposes it once the export is read back. It deliberately does NOT reuse whatever session may already be cached for the root or any other Thread, and does NOT leave the fresh one cached afterward either.

**The staleness gotcha this guards against** (found empirically while writing this feature's own contract tests, not merely theorized): `SessionManager.fileEntries` — the array `getEntries()`/`getBranch()` read from — is populated once, when a `SessionManager` instance is constructed (`_setSessionFile`'s `loadEntriesFromFile`), and is updated ONLY by that same instance's own subsequent `appendMessage`/`_persist` calls; there is no re-sync-from-disk on `branch()`, `getEntries()`, or anywhere else in the vendored SDK source. `PiService` caches one `SessionManager` PER THREAD (`threadSessionManagers`, keyed by `thread.id`) and, for real sessions, one `AgentSession` (wrapping its own separate `SessionManager`) PER THREAD too (`this.sessions`, also keyed by `thread.id`) — even though every Thread in a document points at the SAME underlying file. Two threads' own separately-opened/cached instances therefore diverge over time: each instance's own appends ARE flushed to the shared physical file (`appendFileSync`, synchronous), but a DIFFERENT thread's already-open, long-lived cached instance never observes those bytes, since it never re-reads the file after its own initial open. Reusing whichever Thread's session happened to already be cached for the export — the design this project's own task brief initially proposed, before this gotcha was found — would therefore risk silently under-reporting the export: any content another Thread appended AFTER that particular session was first opened would be missing from `getEntries()`, violating FR-013b/SC-006's "matching the document's actual history at export time." Building a genuinely fresh `SessionManager.open()` immediately before the export sidesteps this entirely, since opening always reads the file's current, complete on-disk state at that moment — exactly the same reasoning `exportThreadSession` (R9) already applies for its own, differently-motivated "always throwaway, never the cached instance" rule.

`exportToHtml(outputPath)` (like `createBranchedSession`) writes to a file and returns its path, not the HTML text directly — this method writes to a process-temp path (`node:os` `tmpdir()`), reads it back, and deletes it immediately, mirroring `exportThreadSession`'s own ephemeral, nothing-persisted convention.

**Fake-session caveat**: `FakeAgentSession` (test-mode only, `RADR_BE_PI_FAKE_SESSIONS=1`, never used in production) has no real `AgentSession`/`exportToHtml()` to call — there is no live model or tool-rendering machinery to fake meaningfully for an HTML exporter the way `sendCustomMessage`/`prompt()` are faked for turn execution. Under `config.piFakeSessions`, this method takes a distinct, test-only branch that opens a FRESH `SessionManager.open()` for the document's root Thread's shared file (same staleness reasoning as above — never `this.threadSessionManagers`'s cached instance) and renders a minimal, deterministic HTML stand-in from its `getEntries()`, so the whole-document-export code path — including the "does it actually see every Thread's content" concern — stays genuinely exercisable end to end in contract tests, without a live model in the loop. Production code always takes the `exportToHtml()` branch; the fake branch never runs outside `RADR_BE_PI_FAKE_SESSIONS=1`.

**Rationale**:
- `AgentSession.exportToHtml()` is the SDK's only whole-tree-in-one-artifact primitive (confirmed against the vendored `.d.ts`/compiled source: it internally calls `sessionManager.getEntries()`, the same "every branch" read `readClosedTranscript`/`resolveThreadAnchorEntryId` already treat as safe/side-effect-free) — no other exported SDK surface produces a multi-branch, navigable single artifact.
- Always building fresh (never reusing a cached session, and never leaving the fresh one cached) trades a full model-runtime/tool-wiring cold start on every document-wide export for a correctness guarantee that reuse cannot provide — and `exportToHtml()` needs no live model/tool interaction at all, only a correctly-populated `SessionManager`, so the cold-start cost buys nothing reuse would have saved beyond wall-clock time.
- Targeting the root Thread specifically (not an arbitrary one) keeps the fresh-session construction deterministic and gives it the one Thread every threaded-conversation document is guaranteed to have (FR-003/FR-004), rather than requiring a search/priority order across branches — its identity no longer matters for correctness (any Thread's `piSessionPath` would do, since `SessionManager.open()` re-reads the whole shared file regardless of which Thread "owns" the row), only for picking a deterministic one to hand to `getOrCreateSession`.

**Alternatives considered**:
- Building an HTML export from the application's own event log (reformatting `buildConversationMessages` output across every Thread into a hand-rolled multi-branch viewer). Rejected outright: this is exactly the "fabricated/reconstructed substitute for Pi's own export" the constitution's carve-out (v2.4.0, extended v2.5.0) explicitly excludes.
- Reusing whichever Thread already has a live cached session in `PiService.sessions` as a "cheap path," falling back to a cold start only when nothing is cached. This was the design initially proposed for this feature and is rejected here: per the staleness gotcha above, a cached session's own `SessionManager` can be arbitrarily out of date relative to a sibling Thread's more recent, separately-flushed appends, so this "cheap path" could silently produce an incomplete export — a correctness defect FR-013b/SC-006 cannot tolerate, for a cost saving (avoiding one cold start) that does not scale with how often the export action is actually used.
